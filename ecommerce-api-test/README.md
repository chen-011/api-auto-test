# 电商订单系统 · 接口自动化测试

基于 Python + pytest + requests 的接口自动化测试项目，被测对象是一个模拟真实电商业务的订单服务（登录鉴权 → 商品查询 → 下单 → 库存扣减 → 满减计算 → 订单查询）。

## 一、项目亮点

| 亮点 | 说明 |
|---|---|
| **32 条用例，6 类场景** | 登录鉴权、下单正常流、参数异常流、满减边界、并发超卖、重复提交幂等 |
| **真实缺陷发现** | 被测服务内置 4 类电商典型缺陷，用例跑出 4 条失败，逐个定位到代码根因 |
| **闭环验证** | 修复后回归 32 条全部通过（4 failed → 32 passed） |
| **数据驱动** | 用例写在 `cases.csv`，新增用例零改代码 |
| **用例独立性** | 每条用例前自动重置数据，避免用例互相污染 |

## 二、目录结构

```
电商接口测试项目/
├── mock_server.py          被测服务（含 4 个已知缺陷）
├── mock_server_fixed.py    被测服务（修复版，用于回归验证）
├── conftest.py             pytest 配置：启动服务、登录态、数据重置
├── test_order.py           主测试集：21 条用例
├── test_data_driven.py     数据驱动测试：11 条用例（读 cases.csv）
├── cases.csv               用例数据表
└── requirements.txt        依赖清单
```

## 三、如何运行

```bash
pip install -r requirements.txt

# 测「有缺陷版」，应看到 4 条失败
python -m pytest test_order.py test_data_driven.py -v

# 测「修复版」，应看到 32 条全部通过
MOCK_VERSION=fixed python -m pytest test_order.py test_data_driven.py -v
```

## 四、发现的 4 个缺陷

### 缺陷 1：并发超卖（严重）

- **现象**：库存 5 件，10 个请求同时抢购，成功下单 10 单，库存变成 -5
- **用例**：`test_concurrent_oversell`
- **根因**：先查库存、后扣库存，两步之间没有锁保护。并发时多个请求同时通过"库存充足"校验，然后各自扣减
- **修复**：把「校验库存 + 扣减库存」放进同一把互斥锁内，保证原子性
- **业务影响**：超卖会导致用户付款后无货，需赔付或强制退款

### 缺陷 2：满减门槛差一错误

- **现象**：满 500 减 50 的活动，正好 500 元不减（实付 500，应为 450）
- **用例**：`test_full_reduction_exact_500`、`test_order_from_csv[TC07]`
- **根因**：判断写成 `amount > 500`，应为 `amount >= 500`
- **修复**：改为 `>=`
- **业务影响**：用户投诉"说好的满减没减"，属于资损与口碑问题

### 缺陷 3：重复提交产生两笔订单

- **现象**：同一 `request_id` 提交两次，生成两笔订单，库存扣了两次
- **用例**：`test_idempotent_submit`
- **根因**：服务端没有幂等键校验
- **修复**：用 `request_id` 做去重缓存，重复请求直接返回已有订单
- **业务影响**：用户手抖连点或网络重试会被重复扣款

### 缺陷 4：库存扣减未二次校验

- **现象**：与缺陷 1 同源，单线程下单正常，并发下库存被扣成负数
- **修复**：锁内二次校验库存，不足则拒绝

## 五、测试设计思路

1. **先划分场景**：把下单链路拆成「鉴权 → 参数 → 库存 → 金额 → 并发 → 幂等」六段，每段独立设计用例
2. **异常优先**：正常流只需 1-2 条，重点放在参数异常、库存不足、未登录等分支上
3. **边界必测**：满减规则的关键是「正好 500」这个点，差一错误只会在这里暴露
4. **并发单独建用例**：单线程跑不出超卖，必须用线程池模拟真实抢购
5. **每条用例独立**：靠 fixture 重置数据，保证失败可复现、不影响其他用例
